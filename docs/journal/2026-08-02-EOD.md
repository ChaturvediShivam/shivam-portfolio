# Executive Summary

Today was a long day split into two distinct work arcs, and the second one is the one that matters architecturally.

The **first arc (00:18 → 03:23)** closed out the CRM's AI feature set. Three things landed: M9 (AI email drafting, approval-gated, sent through Gmail), M10 (declarative workflow automation — a trigger→conditions→actions rule engine stored as data), and an inbox triage assistant that reuses the existing gateway with no new infrastructure at all. Together these were ~8,100 lines across 65 files and took the suite from 223 to 378 tests. The through-line in all three is the same: **a machine may propose, only a human may cause an irreversible effect.** M10's `change_stage` and `draft_email` actions do not execute — they write an `ai_approvals` row and stop, so M9's human gate stands between an automation rule and anything that leaves the building. That is not a UX decision, it is the safety property that makes an autonomous rule engine acceptable to run at all.

The **second arc (15:09 → 22:26)** built the Resume AI feature from an empty page to a working end-to-end analysis, in four deliberate layers, each shipping before the next was designed:

1. **Upload (`929046d`, 15:09).** `/admin/resume-ai` with two uploaders, dual extension+MIME validation, and modelled-but-unreachable `transferring`/`processing` states. Plus `lib/resume/placeholder.ts` — a bodiless seams file that fixed the shape of every later step *before* any of them was written, specifically so the upload flow could not be designed in a way that would fail to carry them.
2. **Parser (`5662bdd`, 16:17).** Deterministic PDF and DOCX text extraction, entirely client-side. DOCX takes **zero dependencies**: a DOCX is a ZIP, `DecompressionStream("deflate-raw")` is now native, so ~100 lines of ZIP central-directory walk replaces ~100 KB of `jszip` in the client bundle. PDF takes `pdfjs-dist` deliberately, because PDF stores glyph codes and not text, and font-encoding resolution is not a thing to hand-roll.
3. **Deterministic analysis (`4a4deda`, 21:09).** The day's central architectural inversion: **an analysis is no longer something an LLM produces, it is something an LLM later enriches.** Skill matching, keyword extraction, experience/education comparison and a weighted five-category score, all pure arithmetic over evidence, all running in the browser in about a millisecond. Every match carries the resume line it came from.
4. **AI intelligence layer (`fcd0aaf`, 22:01).** The first server-side step in the feature. Four gateway calls — one `resume_review` plus three enrichments settled independently — behind `FEATURE_RESUME_AI`, off by default.

The reason step 4 is defensible rather than reckless is **grounding enforced in code, not in the prompt**. `AiResumeInsights` has no score field, so there is physically nowhere for a model to write a number that competes with the engine's. Every claim the model returns is then checked against the deterministic result before it reaches the operator: evidence must quote text that was actually supplied, `criticalGaps` may only name skills the engine already reported missing, `transferableSkills` may only start from a skill the parser detected, `missingKeywords` is intersected with the engine's own list. Anything that fails is discarded and recorded in `dropped[]`, which is rendered — so a drifting model becomes *visible* rather than merely plausible. The prompt states the rules too, but the prompt is the polite request and the type system plus `lib/ai-analysis/grounding.ts` are the enforcement.

The call was also moved to a Server Action rather than left in the browser, and the deterministic analysis is **recomputed server-side rather than accepted from the client** — same pure function, same parsed resume, identical result, but now engine-produced on the server, so a crafted request cannot hand the model a fabricated score to explain.

Why it moves the project forward: before today, the AI layer in this codebase was infrastructure (M6 gateway, budget, audit) with three thin consumers. Today it acquired its most demanding consumer — a multi-call, schema-constrained, grounded, degrading-gracefully feature — and the M6 abstractions absorbed it without a single change to the gateway, the budget ledger, the audit log, or the provider interface. The only edits outside the new modules were five lines in `lib/ai/prompts/registry.ts` and one flag in `lib/featureFlags.ts`. That is the strongest evidence yet that the M6 design was right.

Net for the day: **+17,926 insertions / −26 deletions across 129 files**, 108 new files, 11 commits (8 substantive, 3 merges), and the test suite grew from **223 to 621 tests (+398, +178%)** across **17 → 39 files**.

The honest caveat, stated once here and repeated where it matters: **none of the AI paths have run against a real model.** Deterministic layers were verified against real files in a real browser (a real 10.8 MB PDF, a real DOCX fixture scoring 87/100). The AI layer has been verified only against fakes. Until a provider key exists and one real review is run end to end, the AI half of the Resume AI feature is *believed correct*, not *known correct*.

# Major Milestones Completed

## Milestone 1 — M9: AI email drafting, approval-gated, sent via Gmail (`b0356b6`, 00:18)

**Purpose.** ADR-006 required a human-in-the-loop queue before any AI-initiated write or external effect. M6 shipped the *policy* that refuses unapproved execution but registered no write tools, so the queue had no producers and was deferred. M9 is what finally gives that policy something to govern.

**Technical implementation.** Four layers, deliberately separated by the approval gate:

- **`ai_approvals` table + state machine (`lib/approvals.ts`, 326 lines).** Every transition is a *conditional update naming the status the caller believes it is moving from*. `claimForSend` moving `approved → sending` is the load-bearing one: whoever wins the update owns the effect, every other caller gets `null`, and nothing may call Gmail without holding that claim. Idempotency is layered twice — a partial unique index on `idempotency_key` plus the conditional transitions.
- **Gmail send (`lib/integrations/google/gmail.ts`).** `buildRawMessage` is pure and exported precisely because it produces the exact bytes that reach a real inbox — it deserves direct assertions, not a mock. Subject and recipients originate from model output and are therefore stripped of CR/LF before touching a header. A value carrying a newline terminates the current header and begins one the caller never wrote; that is how a "reply" quietly acquires a `Bcc`. Malformed addresses are dropped; a message with no valid recipient refuses to build rather than sending to nobody. Non-ASCII subjects are RFC 2047 encoded; the body is base64'd so arbitrary prose cannot alter the MIME structure.
- **Drafting (`lib/ai/drafting.ts`, 247 lines).** **Drafting never chooses recipients.** Addresses are derived from the synced message being replied to, so nothing written *inside* an email the operator received can redirect the reply that answers it. The model chooses words; this module chooses who receives them. A test asserts that model output naming its own recipients is simply not read.
- **Executor (`lib/ai/send.ts`, 261 lines).** Ordered entirely around irreversibility: claim first → resolve token → send → **mark sent BEFORE writing CRM rows.** Past that line the mail exists, and reporting failure would invite a retry that could only duplicate it, so post-send bookkeeping errors are logged rather than raised.

**Architecture decisions.** `status` is `text` with a `CHECK` rather than a native enum, matching the `ai_*` family — these vocabularies still move between milestones, and a `CHECK` change is not a migration where an enum change is. `proposed_payload` is the complete frozen instruction set; nothing about the outbound mail is recomputed at send time, or approving would not mean approving what the operator actually read.

**Files affected.** 29 files, +2,884 / −12. New: `lib/approvals.ts`, `lib/ai/drafting.ts`, `lib/ai/send.ts`, `lib/ai/prompts/templates/email-reply.ts`, `types/approval.ts`, `supabase/migrations/20260801090000_ai_approvals.sql`, `app/admin/(dashboard)/approvals/*`, `components/admin/approvals/{ApprovalCard,DraftReplyPanel}.tsx`. Modified: `lib/integrations/google/{gmail,oauth}.ts` (the `gmail.send` scope, requested via incremental auth), `lib/featureFlags.ts`, `lib/admin/navigation.ts`.

**Testing performed.** 51 new tests across `test/ai/approvals.test.ts` (13), `test/ai/drafting.test.ts` (13), `test/ai/send.test.ts`, `test/integrations/gmail-send.test.ts` (9). Weighted toward the transition predicates: *a transition that dropped its predicate would look identical in the happy path and only diverge under a race*, so each is asserted to actually reach the database.

**Browser verification.** The queue UI, the two-press approve→send flow, and the draft panel were built and rendered. No evidence in the workspace of a real Gmail send.

**Production verification.** None. `FEATURE_EMAIL_DRAFTING=false`, nothing deployed.

**Remaining limitations.** `gmail.send` is a *restricted* scope requiring Google verification before production use. Anyone who connected their account before M9 must reconnect. A row stranded in `sending` by a crashed request is recoverable only by operator-driven `dismiss`, which deliberately makes **no claim about whether the mail went out** — after a crash nobody can say, so retrying risks a duplicate and marking it failed risks denying one that was delivered. The UI says exactly that: check your sent mail before drafting another.

## Milestone 2 — M10: Workflow automation, a declarative rule engine (`78ff54c`, 00:49)

**Purpose.** Turn repeated manual CRM operations into stored, auditable rules evaluated off the request path.

**Technical implementation.** `trigger → conditions → actions`, stored as data (`lib/automation/{schema,rules,conditions,actions,engine,emit,trigger}.ts`, ~1,700 lines) with a structured editor (`RuleForm.tsx`, 429 lines) rather than a JSON box.

The DSL is the **only** place this system accepts user-authored logic, so validation **rejects rather than ignores**. An unknown action silently dropped would arm a rule the operator believes does something else; a condition naming a non-existent field would become a rule that never fires — the most expensive automation bug to diagnose. Condition fields are allow-listed *per trigger entity*, so a condition can never read a column the UI would not show, and values are type-checked against enum domains.

Cron support is a **real matcher, not a stub**, for the same reason: accepting syntax the matcher does not implement produces a rule that silently never runs. Names and the non-standard `?`/`L`/`W` forms are rejected. `isSchedul­eDue` walks every minute since the last run rather than testing "now", because the scan cadence is coarser than a cron minute and a 09:00 rule would otherwise be skipped whenever no scan happened to land in that minute.

**Architecture decisions — loop safety is three independent bounds**, because each alone has a hole:
1. A per-`(rule, entity)` cap inside a cooldown window.
2. A unique index on `(rule, event)` **claimed before actions execute** — this is what converts the job queue's at-least-once delivery into exactly-once *execution*.
3. Approval gating, so the worst a runaway loop can produce is a queue of proposals nobody approves.

The cap counts only runs that *executed* something, or a rule seeing many non-matching events would throttle itself out of ever firing. Actions route through the same `lib/*` functions the UI calls, so validation, owner scoping and timeline events apply identically whether a human or a rule acted.

**Files affected.** 35 files, +4,304 / −15, including `supabase/migrations/20260802090000_automation.sql`, two job handlers, and `types/automation.ts`.

**Testing performed.** 98 new tests across six files, weighted toward rejection and safety cases.

**Browser verification.** Rule editor built and rendered; the run log sits next to the rule it explains, because *a rule that is not firing and a rule that is firing and matching nothing look identical from outside*.

**Production verification.** None. `FEATURE_AUTOMATION=false`.

**Remaining limitations / what self-review caught.** Three review passes found three real defects, each documented in the commit body:
- Schedule rules **would never have fired** — the `automation_scan` chain is self-perpetuating and nothing enqueued the first one.
- The chain could **die permanently** — a scan that threw skipped its own follow-up. Rescheduling moved into `finally`.
- A run claimed for execution was recorded as `skipped` with reason "Executing…" — *a lie in the run log, and it matters precisely when things go wrong.* A `running` status now exists, deliberately never auto-reclaimed.
- The loop governor counted only terminal runs, so an in-flight or crashed execution quietly freed budget. It now counts `running` too.

## Milestone 3 — AI Inbox Assistant (`0770f57`, 03:17)

**Purpose.** An on-demand pass over recent inbound mail that surfaces what is actually waiting on the operator.

**Technical implementation.** The cheapest possible feature, by design: **no new infrastructure.** One prompt template, one decision module (`lib/ai/inbox.ts`, 248 lines), one Server Action, one panel. No migration, no new table, no new column, no queue work. It reuses the M6 provider abstraction, token budget, audit logging and prompt registry exactly as they are.

**Architecture decisions.** Nothing is persisted and nothing is computed on page load — the digest is produced when the operator presses the button and lives in page state. The only durable trace is the `ai_audit_log` row the gateway already writes. That keeps a *billable call* off the render path of a page people open constantly.

Messages are referenced by **a small integer ref rather than a UUID**, and every ref that comes back is validated against the candidate list actually sent. Anything invented, duplicated, or out of range is dropped rather than rendered — *a digest citing a message the operator cannot open is worse than no digest.* `noActionCount` is derived from what survived mapping, not from the model's own arithmetic. This is the same grounding discipline that later became `lib/ai-analysis/grounding.ts`; the inbox assistant is where the pattern was first proven.

Message bodies are attacker-authorable, so they are delimited and the system role states that delimited content is data. Where an M7 summary exists it is preferred over the raw body — shorter, already redacted, says the same thing.

**Files affected.** 11 files, +923 / −1.

**Testing performed.** 16 new tests, weighted toward ref mapping and output bounding.

**Browser verification.** Panel built. No evidence of a real provider call.

**Remaining limitations.** An empty inbox and a "nothing needs you" result are treated as successes, not errors — reporting them as failures would train the operator to ignore the panel.

## Milestone 4 — Resume AI Step 1: upload flow and module scaffold (`929046d`, 15:09)

**Purpose.** Ship the upload half of the Resume AI feature — UI and architecture only. No AI call, no parser, no storage, no API route.

**Technical implementation.** `/admin/resume-ai` with a stateful container (`ResumeAiWorkspace.tsx`) driving two controlled uploaders, so the Analyze button can know whether it can run without either uploader knowing the other exists. Shared upload primitives live in `types/upload.ts` because the resume and the job description are *different domains but the same upload problem*; writing it once stops the two drifting.

**Architecture decisions.**

- **Validation checks extension AND MIME and trusts neither alone.** `File.type` is frequently empty for a legitimate `.docx`, so requiring a MIME match would reject real resumes; an extension alone lets `payload.exe` renamed `resume.pdf` through. So: the extension must match, and the MIME must agree *or be absent*. Content sniffing is left to the step that reads the bytes.
- **`transferring` and `processing` states are modelled and rendered but unreachable.** Nothing leaves the browser yet. They exist so the step that adds a real transfer replaces the body of `useDocumentUpload.accept` and changes nothing else — and so they are never first exercised in production.
- **`lib/resume/placeholder.ts` — interfaces only, no bodies.** This is the most unusual artifact of the day and the one most likely to be misread later. It fixes the shape of Step 2 *before* Step 2 is written, so the Step 1 upload flow cannot be designed in a way that will not carry it. Three constraints, each mirroring the existing AI layer: **no vendor names** (`ResumeAnalyzer` takes an `AiGateway`, not a provider client, so flag gating / budget / redaction / audit cannot be bypassed); **parsers are an interface, not a function** (PDF and DOCX libraries are heavy enough that the choice should stay swappable); **extraction is separate from analysis** (parsing is cheap and deterministic, analysis is billed and non-deterministic — so a re-analysis never re-parses, and a parser bug can be fixed and re-run without spending tokens).
- **No feature flag.** The page made no AI call and stored nothing, so there was nothing to gate. A flag was added only when Step 2 introduced the first billed call.

**Files affected.** 19 files, +1,721. All new.

**Testing performed.** 25 tests covering validation, weighted toward rejection cases — *an accepted file we cannot read surfaces much later as a confusing parse failure.*

**Browser verification.** Merged to `main` via PR #5 at 15:14 and exercised in the browser.

**Production verification.** None; not deployed.

**Remaining limitations.** State is local and unpersisted — a reload clears the form. That is the honest behaviour while there is no durable store to reload from.

## Milestone 5 — Resume AI Phase 2: deterministic PDF and DOCX parser (`5662bdd`, 16:17)

**Purpose.** Turn an uploaded file into normalized text with detected sections, entirely client-side and entirely deterministic. No model involved.

**Technical implementation.**

- **`lib/resume/parsers/zip.ts` (142 lines) — no ZIP dependency.** A DOCX is a ZIP; the only entry that matters is `word/document.xml`; reading it needs a central-directory walk and an inflate, and the platform now provides `DecompressionStream("deflate-raw")` in every browser this admin supports and in Node 18+. `jszip` and friends are ~100 KB of client bundle to read one file out of one archive.
- **`lib/resume/parsers/docx.ts` (111 lines).** WordprocessingML walked with a **tokenizer, not `DOMParser`** — `DOMParser` does not exist in Node, so a DOM-based extractor could not be unit tested. Only four elements matter: `<w:t>` (the payload), `<w:p>` (the only reliable line boundary), `<w:br>`, `<w:tab>` (which on a resume separates a role from its dates and must not silently concatenate them). Headers, footers, footnotes and comments are deliberately skipped — on a resume they hold page numbers and template boilerplate.
- **`lib/resume/parsers/pdf.ts` (169 lines) — `pdfjs-dist`, deliberately.** PDF stores glyph codes, not text. Recovering characters means resolving WinAnsi, MacRoman, and Identity-H with embedded CMaps, and subset fonts with custom differences arrays. A hand-rolled content-stream reader works on the PDF you test with and emits mojibake on the next one — and a resume exported from Canva, LaTeX and Word will exercise all three paths. **The only PDF logic this project owns is `itemsToLines`**, which reassembles positioned fragments into lines: group by baseline (`transform[5]`) with a 2-unit snap so sub-pixel drift does not split a line, sort descending because PDF's origin is bottom-left, then order left-to-right within a row. A horizontal gap wider than 8 text-space units becomes a **tab** rather than a space — on a resume that gap *is* the space between a job title and its dates. It is exported and tested directly because that is where the interesting mistakes live.
- **`lib/resume/sections.ts` (266 lines).** Section detection is a **lookup table, not a heuristic pile.** The bias is deliberately toward *missing* a heading rather than inventing one: a missed heading merges two sections and leaves the text intact, while a false heading splits a bullet list mid-way and makes content look truncated.

**Architecture decisions.** The pdf.js worker is copied to `public/` by `scripts/copy-pdf-worker.mjs` on every `prebuild` and `predev`, and gitignored. This is not the obvious choice and the reasoning matters: resolving the worker through the bundler with `new URL("pdfjs-dist/...", import.meta.url)` makes webpack treat the worker as *source*, and SWC then rejects it with *"'import', and 'export' cannot be used outside of module code"*. Copying sidesteps the bundler entirely, serves the worker as a static file at a stable path, and — because the copy runs on every build — keeps the worker version-locked to the installed `pdfjs-dist`, which is the drift failure a committed vendored copy would eventually hit.

**Files affected.** 17 files, +2,275 / −2. Adds `pdfjs-dist@^4.10.38` (the day's only new runtime dependency), `scripts/copy-pdf-worker.mjs`, and `prebuild`/`predev` hooks.

**Testing performed.** 83 new tests across normalization, section detection, DOCX/ZIP (**including a real DEFLATE round-trip**, not a fixture), and PDF line assembly. Three bugs were caught by their own tests before shipping (see *Bugs Found*).

**Browser verification.** ✅ Real. Merged to `main` via PR #6 at 17:06 and exercised against real files.

**Production verification.** ✅ Partial and real — the `e50f723` bug was **found by uploading a real 10,856,561-byte PDF to the preview deployment.** That is the only genuine deployed-environment verification of the day.

**Remaining limitations.** No OCR — a scanned/image PDF yields a warning saying exactly that, which is far more useful than an empty string the UI would render as a successful parse of nothing. The ZIP reader handles STORE and DEFLATE only; no ZIP64, no encryption, no multi-disk. This is marked in-code with a `ponytail:` comment naming the ceiling and the upgrade path (reach for a library rather than growing this).

## Milestone 6 — Resume AI Phase 3 Step 1: deterministic analysis engine (`4a4deda`, 21:09)

**Purpose.** Score a parsed resume against a job description with no model involved.

**Technical implementation.** Seven modules under `lib/resume-analysis/`, composed by `ResumeAnalysisService.ts` which *owns nothing but the order*:

- `JobDescriptionParser.ts` (341 lines) — structure out of raw posting text.
- `KeywordExtractor.ts` (149) — unigrams and bigrams.
- `SkillMatcher.ts` (208) — a **curated dictionary with a directional relation graph**.
- `MatchingEngine.ts` (245) — skills, experience, education, keywords, responsibilities.
- `ScoreCalculator.ts` (276) — the weighted score.
- `RecommendationEngine.ts` (53) — **interfaces only**, deliberately.

Weights: skills 0.35, experience 0.30, keywords 0.15, education 0.10, responsibilities 0.10. `ENGINE_VERSION = "1.0.0"`, bumped whenever weights or formulas change.

**Architecture decisions.** Three, and they are the day's most important:

1. **An analysis is not something an LLM produces; it is something an LLM later enriches.** Scores, matches and gaps are reproducible, free, instant and auditable — properties a generated number cannot have. This inverted the Phase 1 placeholder, so the `ResumeAnalysis` declared there is superseded by `types/resume-analysis.ts` and `ResumeAnalyzer` is marked superseded in the seams file rather than left to rot as a second incompatible type with the same name.
2. **Required skills dominate the skills category** (`REQUIRED_SHARE = 0.8`), each side scored independently and blended, so a candidate cannot offset a missing must-have by matching many nice-to-haves. A `related` match earns 60% credit — real evidence, but weaker than naming the skill.
3. **A category the posting did not specify scores full marks, not zero.** Punishing a candidate for the employer's silence would be wrong. The missing signal is charged to **confidence** instead, reported separately — because a resume can score 80 purely because the posting asked for almost nothing, and the operator needs to be able to see that.

Skill matching is a curated dictionary rather than similarity, because **string distance matches "Java" to "JavaScript" and a model invents skills the resume never claimed** — both inflate a score with evidence that does not exist. Relations are directional (Kubernetes evidences Docker, not the reverse) and never inferred from spelling. Every match carries the resume line it came from: *a score the operator cannot trace back to their own words is a score they have no reason to trust.*

`RecommendationEngine` is interfaces only because producing recommendations needs judgement rather than arithmetic — precisely the boundary between this step and the AI one. The field exists so the UI that renders advice is written once.

**Files affected.** 15 files, +2,583 / −35. New `types/resume-analysis.ts` (244 lines), `components/admin/resume-ai/AnalysisResults.tsx` (278 lines).

**Testing performed.** 79 new tests across three files. Three bugs caught by their own tests (see *Bugs Found*).

**Browser verification.** ✅ Real and specific: verified end to end against the real DOCX fixture — **87/100, confidence 1.0, 4 of 4 required skills matched, Rust correctly reported missing.**

**Production verification.** None. Branch not merged, not deployed.

**Remaining limitations.** The skill dictionary is curated, so coverage is exactly as good as the dictionary. Nothing is persisted; every analysis is recomputed.

## Milestone 7 — Resume AI Phase 3 Step 2: AI intelligence layer (`fcd0aaf`, 22:01)

**Purpose.** Enrich the deterministic analysis with an AI review that *explains* the score and never computes one.

**Technical implementation.** Fifteen modules under `lib/ai-analysis/`, plus five prompt templates and a Server Action.

**Shape of the work** (`ResumeInsightsService.ts`, 291 lines):
1. One `resume_review` call, whose reply is passed through the analyzers. Everything ungrounded is discarded there and recorded in `dropped`.
2. Three enrichment calls — interview questions, LinkedIn copy, summary rewrite — issued together via `Promise.allSettled` and settled **independently**, so a failure in one costs only that panel. `allSettled` rather than `all` because losing all three because the LinkedIn call hit a rate limit is a worse outcome than showing two. Failures are logged, not surfaced: the operator asked for an analysis, and an error banner about a side panel they did not ask about is noise.
3. The cover letter is **not** here. It is outward-facing text the operator sends under their own name, so it stays an explicit separate action behind its own button — the same reasoning that keeps M9's email drafts from being written automatically.

**Retry policy.** The primary review retries **once**, and only on `AiTransientError`. A refusal, a budget stop, or a schema violation will fail the same way twice, and retrying them would double the spend to reach the same answer. The enrichment calls are not retried at all.

**Input ceilings.** `MAX_RESUME_CHARS = 14,000`, `MAX_JD_CHARS = 8,000`, plus bounded lists (40 skills, 15 responsibilities, 25 keywords). Generous relative to a resume, tight relative to the model's context — truncating a resume loses the evidence the grounding checks depend on, while an unbounded prompt is an unbounded bill. When truncation does happen, a `TRUNCATION_NOTE` is appended telling the model to judge only what it was shown.

**Architecture decisions.**

- **The prohibition on scoring is structural, not instructional.** `AiResumeInsights` has no score field. There is nowhere for a model to write one. `UnifiedAnalysis` carries the `ResumeAnalysis` through by reference. The prompt states the rule too — but the type system is the enforcement.
- **Grounding is enforced in code** (`lib/ai-analysis/grounding.ts`, 184 lines). `isQuoted` requires ≥12 normalized characters present in the corpus — *below that a quote is not evidence: "and" or "led" appears in every resume.* It is substring-on-normalized rather than exact equality, because models reflow whitespace and drop trailing bullet characters even when told to copy verbatim, and rejecting a real quote over a stray space would discard true findings; what it will not tolerate is different words. `detectedSkill` / `missingSkill` / `knownSkill` bound skill claims to what the engine found. `percent` clamps to 0–100. `items` bounds arrays. `text` caps at 600 chars, `prose` at 4,000 and **keeps line breaks** — a cover letter without paragraph boundaries is not a cover letter.
- **Grounding lives in its own module, not inside the service**, because every analyzer needs it and the service imports every analyzer — putting it in the service would make the import graph a cycle.
- **The call crosses to the server.** `AiGateway` is server-only and needs a Supabase client for flag gating, budget, redaction and audit. A provider call from the browser would expose the key and skip all four. The deterministic analysis is **recomputed on the server** rather than accepted from the client — same pure function, same parsed resume, identical result — so a crafted request cannot hand the model a fabricated score to explain.
- **Trust-boundary bounds on the Server Action payload:** `MAX_RESUME_CHARS = 200,000`, `MAX_JD_CHARS = 100,000`. The parser truncates well below these; the bounds exist because the payload is client-supplied, not because a real resume approaches them.
- **`candidateNameOf` fails closed.** It only accepts a first line of 2–5 words, ≤60 chars, containing no `@`, digit or `|`. Anything ambiguous yields `null` and the letter says "the candidate" — *a wrong guess would put a stranger's name on the operator's letter.*
- **Templates are registered in the existing M6 registry**, not a second one, so there is exactly one place that resolves a template id.
- **`null` insights are a success, not an error.** When the model returns nothing usable, the action returns `actionSuccess` with an explanatory note, because the deterministic analysis on screen is still complete and correct. **Enrichment degrades; the product does not.**

- Analyzers: `StrengthAnalyzer`, `WeaknessAnalyzer`, `RecommendationGenerator`, `ResumeNarrative`, `InterviewQuestionGenerator`, `LinkedInOptimizer`, `ResumeRewriteEngine`, `CoverLetterPrompt`.

# Architecture Decisions

### 1. An analysis is computed deterministically and *enriched* by AI — never produced by AI

**Alternatives rejected.** (a) Send the resume and the posting to a model and ask for a score. (b) Hybrid — let the model score and clamp it against heuristics.

**Why rejected.** A generated score is not reproducible, not free, not instant, and not auditable. Two runs on the same resume produce different numbers, which destroys the operator's ability to A/B their own edits — the *primary* use of this tool. The hybrid is worse than either pure option: it inherits non-determinism *and* adds a clamping layer nobody can reason about.

**Why the chosen design is better.** Scores are arithmetic over evidence, computed in the browser in ~1 ms at zero cost, and every match carries the resume line it came from. The model does the one thing arithmetic cannot: explain, prioritise, and phrase.

**Tradeoffs.** The engine is only as good as its curated skill dictionary and heuristics. It will miss skills a model would catch. That is accepted: a miss is visible and fixable in a table, while an invented match is invisible and inflates trust.

**Long-term implications.** The engine is versioned (`ENGINE_VERSION`), so historical analyses can be interpreted against the formula that produced them once persistence exists. AI enrichment can be swapped, upgraded or disabled without touching a single score.

**Technical debt introduced.** The Phase 1 `ResumeAnalysis` placeholder is superseded, and the seams file now documents a design that was partly overtaken. That is honest debt but it means `placeholder.ts` must be read with its supersession notes, not at face value.

### 2. Grounding enforced in code, not in the prompt

**Alternatives rejected.** (a) Prompt instructions alone. (b) A second "verifier" model call. (c) Trust the schema.

**Why rejected.** Prompt instructions are a request, and a resume review is exactly the task a model will happily invent for — plausible skills, assumed seniority, flattering conclusions. A verifier call doubles cost and latency to check a fallible thing with another fallible thing. A JSON schema constrains *shape*, not *truth*: `{"skill": "Rust", "evidence": "Led Rust migration"}` is schema-valid and completely fabricated.

**Why the chosen design is better.** Every claim is mechanically checked against material that already exists and cost nothing. Evidence must appear in the corpus. `criticalGaps` may only name skills the engine reported missing. `transferableSkills` must start from a detected skill. `missingKeywords` is intersected with the engine's list. Failures are dropped **and recorded in `dropped[]`, which is rendered** — so drift is visible rather than merely plausible.

**Tradeoffs.** False negatives are certain. A legitimate insight phrased with a paraphrase instead of a quote gets discarded. The 12-character minimum and normalized-substring matching are calibrated to reduce that, but the bias is deliberately toward dropping a true claim over admitting a false one.

**Long-term implications.** `dropped[]` is a live quality signal. If a model upgrade causes drop rates to spike, that is observable in the UI today and could feed a metric tomorrow.

**Technical debt.** No aggregate drop-rate metric exists. Per-analysis visibility only.

### 3. AI calls cross to a Server Action; deterministic analysis is recomputed server-side

**Alternatives rejected.** (a) Call the provider from the browser. (b) Accept the client's computed analysis and pass it to the model.

**Why rejected.** (a) exposes the API key and bypasses the flag gate, the token budget, redaction and the audit log — all four of which are server-only. (b) lets a crafted request hand the model a fabricated score to explain, which is a grounding hole exactly as bad as an ungrounded claim.

**Why better.** The analysis function is pure, so recomputation is free and produces the identical result the operator is looking at — but it is now engine-produced on a trusted machine.

**Tradeoffs.** The full parsed resume travels over the wire. Bounded at 200 KB with an explicit trust-boundary comment.

**Long-term implications.** Establishes the pattern for every future Resume AI server step. Once persistence exists, the same action becomes the write point.

### 4. Four calls, one primary and three independently-settled enrichments

**Alternatives rejected.** (a) One giant call returning everything. (b) `Promise.all`. (c) Sequential calls.

**Why rejected.** One giant call needs an enormous output ceiling and fails totally on truncation — and today's uncommitted change shows that ceiling pressure is already real at four. `Promise.all` loses all three panels to one rate limit. Sequential triples latency for no benefit.

**Why better.** Failure is isolated to one panel; latency is one primary call plus one parallel round.

**Tradeoffs.** Four calls cost more than one and produce four audit rows and four budget reservations. Accepted: the budget ledger handles it correctly, and the isolation is worth it.

**Technical debt.** Enrichment failures are `console.error` only. An operator seeing an empty LinkedIn panel cannot distinguish "the model had nothing to say" from "the call failed".

### 5. The cover letter is a separate, explicitly-requested action

**Why.** It is outward-facing prose the operator sends **under their own name**. Producing it automatically as part of a score request conflates two very different consents. The `notes` field exists so the model has somewhere to put what it does not know — notice period, salary expectation, why this company — instead of inventing it, *because a fabricated sentence in a cover letter is one the candidate has to defend out loud.*

**Long-term implications.** Consistent with M9: nothing outward-facing happens without an explicit, separate human press.

### 6. Native platform primitives over dependencies (DOCX), library over hand-rolling (PDF)

The same engineer made opposite calls on the same day, correctly. DOCX: `DecompressionStream("deflate-raw")` is native, so ~100 lines replaces ~100 KB of client bundle. PDF: font-encoding resolution is a genuinely hard problem where a hand-rolled reader silently emits mojibake — so take the reference implementation and own only `itemsToLines`, the ~40 lines where the interesting mistakes actually live.

**Tradeoff.** `pdfjs-dist` is heavy and forced a build-step workaround for its worker.

**Debt.** `scripts/copy-pdf-worker.mjs` and the `prebuild`/`predev` hooks are a real, if small, build-system dependency. If the app ever moves to Turbopack the worker resolution needs re-checking.

### 7. Nothing is persisted — deliberately

**Alternatives rejected.** A `resume_analyses` table alongside the feature.

**Why rejected.** The feature's shape was still moving all day: the `ResumeAnalysis` type was superseded once between Phase 1 and Phase 3 Step 1. A schema written this morning would have needed a migration this evening. And a table nobody reads yet is a migration, RLS policies, an owner-scoping review, and a retention question — all for a feature that has never run against a real model.

**Tradeoffs.** A reload discards everything. A re-run costs tokens again. No history, so an operator cannot compare two versions of their resume — which is arguably the killer feature.

**Long-term implications.** This is the top candidate for the next step, and the deterministic engine's version stamp is already in place to support it.

### 8. Templates registered in the existing M6 registry rather than a Resume-AI-specific one

Adding five templates to `lib/ai/prompts/registry.ts` via cross-module imports slightly muddies the module boundary (`lib/ai` now imports from `lib/ai-analysis`). Accepted, and commented in-place, because *there must be exactly one place that resolves a template id* — a second registry is a second place for a version pin to be wrong.

**Debt.** A one-directional import that runs opposite to the rest of the dependency flow. Watch it if `lib/ai-analysis` ever needs to import from `lib/ai/prompts/registry` at module scope.

# Bugs Found

## Bug 1 — Oversized-file rejection message contradicted itself (FIXED, `e50f723`)

**Root cause.** `formatFileSize` rounded anything at or above 10 MB to a whole number: `mb < 10 ? mb.toFixed(1) : Math.round(mb)`. The limit is exactly 10 MB, so *every* oversized file rendered as "10 MB" — identical to the limit it was being compared against.

**Symptoms.** `"That file is 10 MB. The limit is 10 MB."` The sentence contradicted itself precisely when the operator most needed it to be clear.

**Reproduction.** Uploading a real 10,856,561-byte PDF to the **preview deployment**. Not found by reading the code — and notably, *every unit test passed both before and after*, because they only asserted sizes where the rounding happened to agree.

**Fix.** Megabytes now keep one decimal, dropped when whole: `Math.round((kb / 1024) * 10) / 10`, formatted with `Number.isInteger(mb) ? mb : mb.toFixed(1)`.

**Verification.** The same file now reads "That file is 10.4 MB. The limit is 10 MB."

**Regression protection.** One test asserting both that `formatFileSize(10_856_561) === "10.4 MB"` **and** that it is `not.toBe(formatFileSize(MAX_FILE_BYTES))` — the second assertion is the one that encodes the actual invariant, and it would have caught the original bug where the first alone might not.

## Bug 2 — pdf.js `workerSrc = ""` does not disable the worker (FIXED in `5662bdd`)

**Root cause.** A belief, not a code defect: that setting `GlobalWorkerOptions.workerSrc = ""` runs pdf.js without a worker. pdf.js v4 has **no way** to run without one.

**Symptoms.** `No "GlobalWorkerOptions.workerSrc" specified` thrown at the first parse.

**Reproduction.** Any PDF parse attempt.

**Fix.** Copy the worker to `public/pdf.worker.min.mjs` via `scripts/copy-pdf-worker.mjs`, wired to `prebuild` and `predev`, and point `workerSrc` at that stable path.

**Verification.** Verified against the real library rather than assumed, and 11 PDF tests pass.

**Regression protection.** The misconception is documented **in the source file** with an explicit note that the empty-string idea "is an easy one to have twice." The copy runs on every build, so the worker cannot drift from the installed package version.

**Follow-on defect found while fixing it.** Resolving the worker through the bundler with `new URL("pdfjs-dist/...", import.meta.url)` makes webpack treat the worker as *source*; SWC then rejects it with *"'import', and 'export' cannot be used outside of module code."* This is why the `public/` copy exists at all.

## Bug 3 — Prompt output ceilings too low for the largest structured reply (FIX UNCOMMITTED)

**Root cause.** `resume_review` requested a large structured JSON reply (~3k tokens visible) at `reasoning` task class with `maxOutputTokens: 6144`. **Thinking shares the output ceiling on current models**, so a ceiling sized to the visible answer alone is not enough.

**Symptoms (as documented in the code comment).** The completion returns `stopReason: "truncated"`; the gateway declines to parse a truncated reply (correctly — *"a truncated or refused one has no contract to satisfy"*); `generateInsights` returns `null`; the operator sees *"The AI returned nothing usable for this resume."* And it would fail **on exactly the long resumes the feature is most useful for.**

**Fix.** `resume_review` 6144 → **16384**; `cover_letter`, `interview`, `linkedin` 2048 → **4096**; `rewrite` 1536 → **3072**. Documented with a new docblock in `resume-review.ts`.

**Verification.** ⚠️ **Not verified, and cannot be verified from this workspace.** `.env.local` has no `AI_PROVIDER_API_KEY` and was last written 2026-07-24, so no real completion has been produced here. The change is reasoning-derived and, in my assessment, correct — but the code comment reads as though the truncation was *observed*, and there is no artifact in this repository supporting that. **Resolve before committing:** either confirm it was observed in another environment and keep the comment, or soften it to state the reasoning rather than an observation. A comment that claims an observation that did not happen is worse debt than a missing comment.

**Regression protection.** ❌ **None.** No test asserts that any template's `maxOutputTokens` is adequate — and no unit test *can*, since adequacy is a property of the model. The lazy proxy would be a test asserting the review template's ceiling is at least ~4× its declared schema size; it does not exist.

## Bugs 4–6 — Parser bugs caught by their own tests before shipping (`5662bdd`)

Not production bugs; recorded because the *mechanism* that caught them is the reusable lesson.

- **ASCII-dash bullets survived stripping.** `normalizeCharacters` flattens en/em dashes to ASCII `-`, but the bullet character class never included ASCII `-`. A normalized dash bullet therefore passed through as content. **Two correct transforms, composed in an order neither anticipated.**
- **Unknown-heading false positives.** The title-case branch accepted any capitalised line, so `"TypeScript, Go, PostgreSQL, Kafka"` and `"BSc"` were treated as headings and **emptied the sections above them** — exactly the false positive the design claims to guard against. Now requires all-caps, or a single word of ≥4 letters, and rejects anything containing a comma.
- Both were found by tests written *for the design's stated bias*, not by tests written for the implementation.

## Bugs 7–9 — Analysis engine bugs caught by their own tests (`4a4deda`)

- **A word beside itself became a bigram.** `"kafka kafka"` was emitted as a bigram keyword and **absorbed the real `kafka` unigram**, so a repeated term made itself disappear.
- **Heading tables written with hyphens, normalizer converts hyphens to spaces.** `"nice-to-have skills"` could therefore *never* match, so **every preferred skill was silently misfiled as required** — which would have systematically depressed every score in the most invisible way possible. This is the highest-impact bug found all day.
- **Evidence used a fixed character window**, splicing three partial lines into fragments that read as corruption rather than as a quotation — directly undermining the "every match carries its evidence" contract.

# AI Provider Integration

**Gateway.** `lib/ai/gateway.ts` (445 lines) — the **only** path to a provider. Everything policy-shaped lives there: feature gating, prompt resolution, redaction, budget reservation, tool authorization, output validation, audit. No caller can obtain a completion that skipped any of it. Today's work added the most demanding consumer it has yet had — four calls, schema-constrained, retried, degrading — **and required zero changes to the gateway.**

It depends on the `AiProvider` interface and never on a concrete adapter, so the whole file is exercised in tests against a provider that has never heard of any vendor. `test/ai/neutrality.test.ts` is the standing proof.

**Provider.** `lib/ai/providers/index.ts` resolves `AI_PROVIDER` (default `anthropic`) to `AnthropicProvider`, memoised per process because adapters hold an HTTP client. **It is the last file in the dependency chain allowed to name a vendor.** Adding a provider is one directory plus one `case`. Fails closed: no key → `AiUnconfiguredError`; unknown name → `AiUnconfiguredError`.

This project calls the Anthropic API directly via `@anthropic-ai/sdk@0.115.0`, **not** through Vercel AI Gateway. That remains a viable future consolidation but was not touched today.

**Environment variables** (all server-only, all documented in `.env.example`):

| Variable | Role | Present in `.env.local`? |
|---|---|---|
| `AI_PROVIDER_API_KEY` | Provider credential | ❌ **No** |
| `AI_PROVIDER` | Adapter selector, default `anthropic` | ❌ No |
| `AI_DAILY_TOKEN_BUDGET` | Per-owner daily ceiling; unset = unlimited | ❌ No |
| `AI_MODEL_FAST` / `AI_EFFORT_FAST` | Cost lever for the `fast` class (`claude-haiku-4-5` / `low`) | ❌ No |
| `AI_MODEL_REASONING` / `AI_EFFORT_REASONING` | Cost lever for the `reasoning` class | ❌ No |
| `FEATURE_AI` | Master gate; gateway is fully inert without it | ❌ No |
| `FEATURE_RESUME_AI` | Today's new flag, off by default | ❌ No (not set anywhere) |

**Audit logging.** `lib/ai/audit.ts` writes one `ai_audit_log` row per provider call: actor, action, entity, provider, model, prompt version, input/output/cached tokens, `cost_micros`, `latency_ms`, outcome, error code, job id, conversation id, owner. **It records references and counts, never prompt or completion bodies** — those live in `ai_messages` when a conversation owns them, and duplicating them would widen the blast radius of a leak for no gain. Error codes are redacted before insertion. **Writing an audit row never fails the caller**: the completion has already been produced and billed, and losing the bookkeeping is strictly better than throwing away real work. A budget refusal is audited *even though no provider call was made*, because it is an operator-visible event.

**Budget ledger.** `lib/ai/budget.ts` — two-phase: reserve an estimate before the call, reconcile to actual after. **The reserve is a single atomic statement in Postgres (`ai_reserve_budget`)**, so concurrent calls cannot both pass the same ceiling — the failure mode a client-side "read total, compare, then spend" check would have. If the commit never lands (crash, or a DB failure after a successful provider call), the reservation stands: that over-counts the day's usage, which is **the safe direction — the budget can under-spend, never over-spend.** A refusal is *permanent for the day* (`AiBudgetExceededError` is non-retryable), so the job runner cannot retry into the same ceiling. If the ledger cannot be consulted at all, it fails closed and does not spend.

Today's Resume AI review reserves and reconciles **four times** per full run. Each is independently audited.

**Token accounting.** Exact when the provider offers `countTokens`; otherwise a deliberately pessimistic estimate at ~3 chars/token (rather than the usual ~4) **plus** `maxOutputTokens`, so the budget over-reserves — under-reserving would let a call slip past the ceiling. Counting failures fall back to the estimate rather than blocking the call. Note: today's ceiling raise (6144→16384) **increases the reservation for every review call by ~10k tokens**, whether or not the model uses them.

**Latency.** Accumulated across tool rounds and reported per call in `latency_ms`. No target, no alerting, no measured real-world figure — the AI path has not run.

**Cost.** `estimateCostMicros(model, usage)` per call, summed across rounds, stored as `cost_micros`. No real cost measured today. Structural expectation: one full Resume AI review = 4 calls, up to ~27 k output tokens across them at the new ceilings, plus input of up to 14 k resume chars + 8 k JD chars per call. **This is by a wide margin the most expensive single operation in the application**, and there is currently nothing preventing an operator from pressing Analyze repeatedly except the daily budget.

**Error handling.** A typed taxonomy (`lib/ai/errors.ts`): `AiDisabledError`, `AiUnconfiguredError`, `AiUnknownTemplateError`, `AiBudgetExceededError`, `AiTransientError` (retryable), `AiPermanentError`. Server Actions surface `AiError` messages directly because they are provider-agnostic and free of request content; anything else becomes a generic message. `AiTransientError` earns exactly one retry on the primary review. Truncated and refused completions are **not parsed** — *a truncated or refused reply has no contract to satisfy, and parsing it would turn a known outcome into a confusing validation error.* Enrichment failures are isolated by `allSettled` and logged.

**Grounding.** Covered in detail above. The mechanism verified today is the code path, not the model behaviour.

**Verified today.** Against an injected fake provider: gateway policy pipeline, prompt registry resolution of all five new templates (versioned `1.0.0`), the four-call orchestration, the `allSettled` isolation, the retry-once-on-transient rule, `null`-on-unusable, and every grounding predicate. **Against a real provider: nothing.**

# Security Notes

**Secrets.** No secret was added, printed, committed, or logged today. `.env.local` is gitignored and was not modified (mtime 2026-07-24). `.env.example` gained four documented placeholder lines. `AI_PROVIDER_API_KEY` is read only inside `lib/ai/providers/index.ts`, which is `server-only`.

**API keys and server-only enforcement.** `lib/ai/gateway.ts`, `lib/ai/budget.ts`, `lib/ai/audit.ts`, `lib/featureFlags.ts`, all of `lib/ai-analysis/*`, and `lib/resume/placeholder.ts` begin with `import "server-only"`. A client component importing any of them fails the build. This is the mechanism that made moving the AI call to a Server Action *mandatory* rather than merely preferable — the browser physically cannot construct an `AiGateway`.

**Environment variables.** Every Phase 3 capability is behind a server-read flag defaulting OFF, and `featureEnabled` requires the string `"true"` exactly — a typo'd value leaves the feature off, which is the safe direction. Twelve flags now exist; `FEATURE_RESUME_AI` was added today. Flag flips are rollbacks that need no redeploy.

**Server Actions re-check the flag.** `analyzeWithAiAction` and `draftCoverLetterAction` both re-check `FEATURE_RESUME_AI` inside the action, not only at render. Server Actions are POST endpoints addressable by id, and **a stale tab is the realistic case during a rollback.** Same discipline as M9's approvals actions.

**Trust-boundary validation.** The Server Action `validate()` runs *before any work is done*: rejects a resume with no `text` string or no `lines` array, resumes over 200,000 chars, empty or non-string job descriptions, and job descriptions over 100,000 chars. Explicitly commented as existing *because this is a trust boundary and the payload is client-supplied*, not because a real resume approaches the limits.

**Client-supplied score cannot reach the model.** The deterministic analysis is recomputed server-side. This closes the most subtle injection vector in the feature: a crafted request handing the model a fabricated score to explain.

**Prompt injection protections.** A resume and a job description are both attacker-authorable in the general case (a posting is copied from the internet; a resume could be supplied by a third party). Defences, layered:
- Delimited content with the system role stating that delimited content is **data, not instructions** — the pattern established in M7, restated in M9 and the inbox assistant, applied here.
- **Structural containment:** even a fully successful injection cannot produce a score, because `AiResumeInsights` has no score field.
- **Grounding:** an injected instruction producing an invented strength gets dropped by `isQuoted` unless the injected text itself is in the corpus — and if it is, it is quoted honestly and visible.
- **Bounded output:** `text` 600 chars, `prose` 4,000, arrays bounded via `items`, `percent` clamped 0–100. A pathological reply cannot become a pathological render.
- **`candidateNameOf` fails closed** — no `@`, no digits, no `|`, 2–5 words, ≤60 chars, else `null`.
- **Inherited from M9:** CR/LF stripped from any model-originated header value; drafting never reads model-chosen recipients.

**Hallucination prevention.** The `dropped[]` array is the security-relevant artifact: it is not just quality tooling, it is the record of what the model tried to assert without evidence, and it is **rendered to the operator**. A model that begins drifting becomes visible in the UI rather than silently authoritative.

**Audit trail.** Every provider call produces exactly one `ai_audit_log` row — including budget refusals with no call, including abandoned streams (under `errorCode: "cancelled"`, so *spend that no one recorded* is the one outcome the streaming path must not have). Bodies are never stored. `owner_id` is on every row.

**Not addressed today.** No rate limiting on `analyzeWithAiAction` beyond the daily token budget — an operator (or a compromised session) can press Analyze repeatedly and burn the day's budget in minutes. No CSP change was needed. The uploaded resume never leaves the browser except as parsed text inside the Server Action payload, and is never written to disk or object storage.

Slowest single file: `test/ai/neutrality.test.ts` at 102 ms (it scans for vendor references). This is the property that makes the tight write-test-fix loop visible in today's commit history possible at all.

**Bundle impact.** `/admin/resume-ai` — **21.3 kB route JS, 132 kB First Load JS.** It is now **the largest route in the application by route-specific JS** (next is `/admin/automations` at 7.29 kB). Shared First Load JS across all routes is 87.6 kB; middleware is 84 kB. The 21.3 kB is the parser, the analysis engine, and three result renderers all shipping to the client — a direct and accepted consequence of the "deterministic analysis runs in the browser" decision. **`pdfjs-dist` is not in that number**: it is dynamically imported inside `extractPdfText`, so it never lands in a server bundle and costs nothing on a page that does not parse a PDF. The worker is a separate static asset from `public/`.

**Latency.** Deterministic analysis: **~1 ms**, in-browser, per the design note and consistent with the 431 ms total test execution across 621 cases. PDF/DOCX parsing: unmeasured, worker-threaded, bounded by page count. AI review: **unmeasured** — structurally one review call plus one parallel round of three, so roughly `latency(review) + max(latency(interview), latency(linkedin), latency(rewrite))`. The gateway records `latency_ms` per call and accumulates across tool rounds, so real figures will appear in `ai_audit_log` the first time it runs.

**Memory.** Explicitly handled in `extractPdfText`: `page.cleanup()` per page frees the operator list — *without it a long PDF holds every page in memory at once* — and `document.destroy()` runs in a `finally`. The ZIP reader scans at most a 66 KB trailing window for the EOCD record rather than the whole file. Input ceilings (14 k resume chars, 8 k JD chars, 40/15/25-item lists) bound prompt memory. Output ceilings (600 / 4,000 chars, bounded arrays) bound what a pathological reply can allocate.

**Retry logic.** One retry on the primary review, **only** for `AiTransientError` — a refusal, budget stop, or schema violation fails identically twice and retrying doubles the spend for the same answer. Enrichment calls are not retried at all: three more requests to fill a side panel is not a trade worth making. Inherited from M1: the job runner's exponential backoff (`test/jobs/backoff.test.ts`) and self-healing lease reclaim, which do not apply to this inline path.

**Timeout handling.** ⚠️ **Nothing in the Resume AI path sets an explicit timeout.** It relies on the provider SDK's defaults and the platform function timeout (300 s default on Vercel). A hung provider call therefore holds the Server Action for as long as the platform allows. This is a real gap, listed under *Risks Remaining*.

**Cancellation.** The `stream()` path handles it rigorously — an abandoned generator resumes at its `finally`, and **both** the audit write and the budget reconciliation live there, so every reservation produces exactly one audit row and one reconciliation including the abandoned ones. *Spend that no one recorded is the one outcome that must not happen.* The Resume AI path uses `complete()`, not `stream()`, so **there is no client-side cancellation**: if the operator navigates away mid-analysis, the four calls complete and bill regardless. Acceptable for a several-second operation, worth revisiting if latency proves high.

# Lessons Learned

## What worked well

**Shipping in thin, complete layers.** Four Resume AI commits, each independently buildable, testable and mergeable. Two reached `main` the same day. The alternative — one enormous "Resume AI" commit at midnight — would have made the 10.4 MB bug undiscoverable until far later, and would have made the Phase 1 type supersession a much more painful diff.

**Writing the seams file first.** `lib/resume/placeholder.ts` cost maybe thirty minutes at 15:09 and shaped every decision after it. It is why the AI layer plugged into the gateway rather than beside it, why parsing and analysis stayed separable, and why the Step 2 server call was never even *considered* as a browser fetch. Interfaces-with-no-bodies is an unusual artifact, and today it earned its place.

**Enforcing invariants in types, not prose.** `AiResumeInsights` having no score field is worth more than any number of prompt sentences about not scoring. The general lesson: when a rule can be made structurally impossible to break, make it structurally impossible.

**Self-review passes before commit.** M9 had two, M10 had three, and between them they caught: a permanently-stuck state machine row, a schedule chain that would never have started, a schedule chain that could die permanently, a run log that actively lied about what happened, a loop governor that freed budget for crashed executions, and a notification payload hidden behind an `as never` cast. **Every one of those would have passed CI.** None was findable by a test that did not already know to look.

**Tests written for the design's stated bias.** The section detector's design claims "bias toward missing a heading rather than inventing one." The tests written against *that claim* found that the title-case branch was doing precisely the opposite. Testing the stated invariant, not the implementation, is what caught it.

**A fast suite.** 621 tests in 1.62 s. That is what made three self-review-and-fix cycles in one M10 commit practical.

## What did not work well

**The AI layer was built and committed without ever being run.** ~1,900 lines of orchestration, five prompts, and a grounding system, all shipped on reasoning alone. The reasoning is good — but "correct by construction" is a hypothesis, and today ended without testing it. Compounding this, `fcd0aaf` is the **only** substantive commit of the day whose message drops the standing "lint, typecheck, N tests, build green" attestation. When the discipline slips, it slips at the end of a long day on the least-verifiable component.

**Documentation fell behind exactly where it mattered most.** M9 and M10 updated the roadmap, the implementation guide, and the schema reference. The Resume AI track — larger than either, and architecturally more novel — updated nothing. The pattern is clear: docs got written when merging to `main` and skipped when working on a feature branch.

**Uncommitted work at end of day.** Five modified files sitting in the working tree with a comment that may claim an observation that did not happen. Either state is fine; the ambiguity is not.

**Branch hygiene.** Two commits of the day's most valuable work exist in exactly one place on one machine.

## Unexpected discoveries

**`DecompressionStream("deflate-raw")` is genuinely enough to read a DOCX.** ~100 lines replaced a ~100 KB dependency, and the tests round-trip real DEFLATE data. The platform has quietly absorbed a category of dependency.

**pdf.js v4 cannot run without a worker,** and `workerSrc = ""` does not disable it — it produces `No "GlobalWorkerOptions.workerSrc" specified`. The follow-on discovery is more interesting: `new URL("pdfjs-dist/...", import.meta.url)` — the form usually recommended — makes webpack treat the worker as *source*, and SWC then rejects it. Copying to `public/` at build time is the boring solution and the correct one.

**Two correct transforms can compose into a bug.** `normalizeCharacters` correctly flattens en/em dashes to ASCII `-`; the bullet class correctly did not include ASCII `-` (it is a legitimate hyphen). Composed, a normalized dash bullet survived. Neither function was wrong.

**A hyphen convention mismatch silently misfiled every preferred skill as required.** Heading tables were authored with hyphens; the normalizer converts hyphens to spaces; `"nice-to-have skills"` could therefore never match. This would have depressed every score in the application in a completely invisible way, and it was a *data-entry convention*, not a logic error.

**A word beside itself became a bigram.** `"kafka kafka"` emitted a bigram that absorbed the real unigram — repeating a term made it disappear.

**Rounding made an error message contradict itself,** and 83 unit tests did not catch it because they only asserted sizes where the rounding happened to agree. **A real file in a real deployment found it in one upload.**

## Architecture improvements

The **enrich-don't-produce inversion** is the day's principal architectural contribution and generalises well beyond resumes: compute what can be computed, let the model do only what computation cannot, and enforce the boundary in the type system.

**Grounding as a standalone module** with a clear reason (import cycle) turned "we should check model output" into a set of reusable, individually-tested predicates. The pattern started informally in the inbox assistant's ref validation and matured today.

**The M6 gateway proved itself.** The most demanding consumer yet required zero changes to it.

## Testing improvements

**Export the pure core and test it directly.** `itemsToLines`, `buildRawMessage`, `formatFileSize`, every grounding predicate. Where the interesting mistakes live, put the test.

**Real round-trips over fixtures** where feasible — the DEFLATE test compresses and decompresses actual data.

**Regression tests should assert the invariant, not just the value.** The Bug 1 test asserts both `=== "10.4 MB"` *and* `not.toBe(formatFileSize(MAX_FILE_BYTES))`. The second assertion is the one that encodes what actually went wrong.

**The gap to close:** unit tests found seven bugs today; a real file in a real environment found the eighth, and it was the one the user would have seen. Deterministic layers now need to reach real files *earlier*, and the AI layer needs to reach a real model *at all*.

## Development workflow improvements

**Commit messages as the primary engineering record.** Today's messages carry root causes, rejected alternatives, and explicit "this looks wrong and is not" notes. Reconstructing this entire report was possible almost entirely from `git log`. That is a workflow asset worth protecting — and `fcd0aaf` dropping its verification line shows how easily it erodes.

**Merge to `main` early when the layer is complete.** Steps 1 and 2 merged same-day, which is why the preview deployment existed to find Bug 1. Steps 3 and 4 did not, and have no such verification.

**The `ponytail:` comment convention is working.** Two live markers (`zip.ts` ZIP64 ceiling, `retrieval.ts` FTS-only) each name the ceiling *and* the upgrade path. Deliberate shortcuts stay visible instead of rotting into "later means never."

# Personal Engineering Notes

*Written for whoever opens this in six weeks — most likely you, having forgotten most of it.*

## Decisions that must never be forgotten

**The AI does not score. It explains a score that already exists.** If you ever find yourself adding a score field to `AiResumeInsights`, or letting the model adjust `overallScore`, or "blending" the two — stop. The entire value proposition is that the number is reproducible, free, instant and traceable to the operator's own words. The moment a model touches it, all four properties die at once and the tool becomes a slot machine. `AiResumeInsights` has no score field *on purpose*; that absence is a load-bearing structural decision, not an oversight.

**`lib/resume/placeholder.ts` is not dead code.** It has no bodies and nothing calls it. It will look exactly like something to delete. It is the written record of what each later step must satisfy, and it is why the AI layer plugs into the gateway rather than sitting beside it. Parts are now superseded and annotated as such — read the annotations before acting on it.

**Grounding is enforced in `lib/ai-analysis/grounding.ts`, not in the prompts.** If you tune the prompts and think you have improved reliability, you have not touched the actual guarantee. Conversely, if you loosen `isQuoted` (currently ≥12 normalized characters, substring match), you have weakened the *whole* guarantee across every analyzer at once — there is no per-analyzer setting.

**`dropped[]` is a feature, not debug output.** It is rendered. It is how a drifting model becomes visible instead of merely plausible. If someone asks to hide it because it "looks messy," the answer is that the mess is the point.

**The pdf.js worker lives in `public/`, copied at build time, and this is not negotiable.** You will be tempted to "clean it up" with `new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)`. That has already been tried and fails: webpack treats the worker as source and SWC rejects it with *"'import', and 'export' cannot be used outside of module code."* Also: `workerSrc = ""` does **not** disable the worker — v4 has no worker-less mode and throws immediately. Both mistakes are documented in the source. **Note the stale docblock at `pdf.ts:12-16` still describes the `new URL` approach as the correct one** — it contradicts the code below it and should be deleted. Do not let it lead you back into the ditch.

**M9's two-press approve-then-send is deliberate friction.** Someone will call it a bad UX. The extra click is the last reversible moment before mail leaves under the operator's name.

**M10's `change_stage` and `draft_email` never execute.** They write an `ai_approvals` row and stop. That is what makes a rule engine acceptable to run unattended: *an automation may propose; only a person may send.*

## Things you will have forgotten in a few weeks

**"Phase 3" means two different things in this repo.** The CRM track's Phase 3 is M1–M10. The Resume AI track has its own internal numbering (Step 1 → Phase 2 → Phase 3 Step 1 → Phase 3 Step 2) that runs *inside* CRM Phase 3. Commit messages use both. This is genuinely confusing and worth renaming the next time you touch the roadmap.

**Preferred skills were once silently misfiled as required.** Heading tables were written with hyphens; the normalizer converts hyphens to spaces; `"nice-to-have skills"` could never match. Every score was systematically depressed and nothing looked wrong. If a score ever seems mysteriously low, check normalization/authoring convention mismatches first — that class of bug is invisible by construction.

**A word beside itself became a bigram.** `"kafka kafka"` was emitted as a bigram that absorbed the real `kafka` unigram. Repeating a term made it vanish.

**83 unit tests did not catch that error messages contradicted themselves.** The tests only asserted sizes where the rounding happened to agree. A real 10.8 MB PDF on a preview deployment found it in one upload. **Deploy to preview and use it with real files.** That is not a formality.

**The suite runs in 1.6 seconds.** Run it constantly. It is the reason three self-review-and-fix cycles fitted inside one M10 commit.

**Every AI feature ships behind a flag that defaults off, and `featureEnabled` requires the exact string `"true"`.** If a feature appears dead in a new environment, check the literal value before debugging anything else.

## Assumptions made today (and never tested)

1. **That the AI layer works at all.** Everything is against fakes. Verify before believing.
2. **That `maxOutputTokens` at 16384 is enough for `resume_review`.** Reasoned, not measured. And the raise *increases the budget reservation on every call by ~10 k tokens* whether the model uses them or not — a cost you have not yet observed.
3. **That `MIN_EVIDENCE_CHARS = 12` is the right threshold.** Pure judgement. Too high drops real findings; too low admits noise.
4. **That the curated skill dictionary has adequate coverage.** It covers what you thought of on a Sunday.
5. **That `MAX_RESUME_CHARS = 14000` fits a real resume.** Most are two pages, so almost certainly. But the truncation path (`TRUNCATION_NOTE`) has never been exercised against a real model.
6. **That `candidateNameOf` is conservative enough.** It fails closed to "the candidate" — a stranger's name on a cover letter is the failure mode to fear.
7. **That recomputing the analysis server-side always matches what the client displays.** True while the function stays pure. **If anyone ever adds a `Date.now()`, a random seed, or an env-dependent branch to `lib/resume-analysis/*`, this quietly breaks** and the model will explain a score the operator never saw. There is no test asserting client/server parity. Consider adding one.
8. **That four parallel-ish calls per analysis are affordable.** No real cost figure exists.

# Final Assessment

## Architecture quality — 9/10

The strongest dimension by a distance. Today produced a genuinely good architectural idea — *compute what can be computed, let the model do only what computation cannot, and enforce the boundary in the type system* — and then executed it consistently across ~9,800 lines. `AiResumeInsights` having no score field is the kind of decision that stays correct after everyone who made it has forgotten why.

The layering is disciplined: parse → analyze → enrich, each pure where it can be, each independently testable, each shipped before the next was designed. The trust boundary is in the right place and the reasoning for putting it there is written down at the boundary itself. The grounding module's existence is justified by an *import-cycle* argument, which is the kind of concrete reason that survives review.

The strongest single piece of evidence: the M6 gateway, budget ledger, audit log and provider interface absorbed the most demanding consumer they have ever had **without a single change.** Abstractions that hold under a genuinely new load were designed, not guessed.

Marked down one point for a small real wobble: `lib/ai/prompts/registry.ts` now imports from `lib/ai-analysis/`, running against the dependency flow everywhere else. It is commented and the reason (one place resolves a template id) is sound, but it is a boundary the codebase does not otherwise cross.

## Maintainability — 9/10

Unusually high. Comments explain *why*, not what, and consistently document rejected alternatives — `zip.ts` explains why not `jszip`, `pdf.ts` explains why `pdfjs-dist` and why not a hand-rolled reader (and preserves the `workerSrc = ""` misconception because *"the empty-string idea is an easy one to have twice"*). That is writing for a future reader who does not exist yet.

Naming is honest. `placeholder.ts` announces itself as interfaces-only in its first line. `dropped[]` says exactly what it holds. `ENGINE_VERSION` carries "bumped whenever weights or formulas change" right beside it.

The `ponytail:` convention — a deliberate simplification marked with its ceiling *and* its upgrade path — is a genuinely good habit. Two markers exist and both are informative.

Deducted one point for the documentation gap: the roadmap, the project's own declared source of truth, does not know the day's largest feature exists. Excellent in-code documentation and a wrong index is a real maintainability cost, because the index is what a newcomer reads first.

## Scalability — 7/10

Solid where it was designed for and untested where it was not.

Good: the budget ledger reserves atomically in Postgres, so concurrent calls cannot both pass the same ceiling — the exact failure a naive read-compare-spend check would have. M10's exactly-once execution claim converts at-least-once queue delivery correctly. Owner scoping is consistent. The provider abstraction means adding a second vendor is one directory and one `case`. The deterministic engine runs client-side at ~1 ms, so scoring costs the server nothing at any volume.

Less good: no persistence, so every re-read is a recomputation and, for AI insights, a re-spend. No rate limiting beyond a daily token budget. No timeout on the provider call. Four calls per analysis is fine for one operator and would need thought at ten. `/admin/resume-ai` at 132 kB First Load is the app's heaviest route and will grow with the skill dictionary.

None of these are wrong for a single-operator admin tool. They are the correct deferrals — but they are deferrals, and the score reflects the current state rather than the design's ceiling.

## Code quality — 9/10

Consistently high. Small focused modules, pure functions where possible, explicit constants with named reasons (`REQUIRED_SHARE`, `RELATED_CREDIT`, `MIN_EVIDENCE_CHARS`, `COLUMN_GAP`, `LINE_EPSILON` — every one carrying a comment explaining the number). Errors are a typed taxonomy, not strings. `import "server-only"` is applied rigorously enough that the compiler enforces the trust boundary.

Zero lint warnings and a clean typecheck across 471 files after adding 17,926 lines is not trivial.

The bug fixes are particularly good work: each commit body states the root cause, how it was found, why the obvious fix was wrong, and what the regression test actually asserts. The M10 `running`-status fix — *"a run claimed for execution was recorded as skipped with the reason 'Executing…'. That is a lie in the run log, and it matters precisely when things go wrong"* — is exactly the right instinct about honesty in an audit trail.

Deducted for the stale `pdf.ts` docblock that contradicts its own file, and for the comment in `resume-review.ts` that may assert an observation that did not occur. In a codebase where comments are this trusted, a wrong one costs more than it would elsewhere.

## Testing maturity — 7/10

A hard split, and the score is the honest average of two very different halves.

**Deterministic side: 9/10.** 398 tests added in a day, running in 1.6 seconds, weighted toward rejection cases and stated invariants rather than implementation. Seven real bugs caught before shipping. A real DEFLATE round-trip rather than a fixture. Pure cores exported specifically so they can be asserted directly. The Bug 1 regression test asserting *both* the value and the invariant is textbook.

**AI side: 4/10.** Comprehensive against an injected fake and **entirely unexercised against a real provider.** Every fake-based test is a test of your model of the provider, not of the provider. Four calls, five prompts, ten grounding predicates and ~1,900 lines of orchestration have never met a real token.

The other honest deduction: the day's only *user-visible* bug was found by a real file on a preview deployment, not by 83 unit tests — and the tests that existed passed both before and after. That is a known category gap, not a fluke.

## AI readiness — 8/10

The infrastructure is genuinely mature. One gateway with no bypass. Fail-closed flags. Atomic budget reservation that can under-spend but never over-spend. An audit row for every call including refusals and abandoned streams. Redaction before the wire. Vendor neutrality with a standing test to prove it. Prompt templates versioned and resolved from exactly one registry. A typed error taxonomy that distinguishes retryable from permanent.

The grounding work pushes it higher still. Most projects that "use AI responsibly" mean they wrote a careful prompt. This one drops ungrounded claims mechanically and shows the operator what it dropped. Structural prevention (no score field) beats instructional prevention every time, and the codebase clearly knows the difference.

Held at 8 for one reason: readiness that has never been exercised is preparedness, not readiness. The first real call will teach more than the last five hours of building did.

## Production readiness — 4/10

The weakest dimension, and the score is about *this feature*, not the repository — the existing portfolio and CRM (`v1.0.0`) are live and stable and were correctly not touched.

Against production for the Resume AI feature: no live provider verification; two commits unmerged and, until this morning, unpushed; no timeout; no rate limit; no persistence; documentation out of date; and `gmail.send` (M9, also shipped today) requires Google verification before it can be used in production at all.

For it: every flag defaults off, so nothing can leak into production accidentally. Rollback is a flag flip with no redeploy. The deterministic half — which is the majority of the user value — is genuinely production-ready, browser-verified on real files, and would degrade gracefully with the AI flag off. The failure paths are designed: a null result is a *success* with an explanatory note, because the score on screen is still complete and correct.

4/10 reflects "one good day of verification away," not "far from ready."

## Overall project maturity — 8/10

This is a mature codebase. Migrations are versioned. Flags gate everything. Audit trails exist for AI spend. Docs (mostly) accompany features. Commit messages carry engineering reasoning. Self-review passes are habitual and repeatedly find real defects. There is a design system, a component library, an ADR practice, and a roadmap that is normally the source of truth.

The gap between engineering maturity and *operational* maturity is the story: an enormous amount is built, tested and flag-gated, and almost none of Phase 3 has ever run in anger. That is a deliberate and defensible strategy — build dark, flip carefully — but it means the verification debt compounds quietly with every milestone.
